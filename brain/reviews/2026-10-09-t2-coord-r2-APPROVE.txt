NEW NON-BLOCKING OBSERVATIONS (Round 2)
=====================================================================
1. Intentional incremental/cold asymmetry for revoked genese: the
   incremental path preserves revoked history (complete:true), whereas a
   cold rebuild of the SAME revoked state drops it entirely (my scratch
   output: incremental G1 = [QmD1V0, QmD1C, QmArchItem1] vs revoked-cold
   G1 = [QmArchItem1]). This is the design intent of a history-preserving
   inventory and the view is self-consistent, but note that any transient
   complete:false that triggers a cold rebuild permanently drops the
   revoked history from the cache. No test pins this asymmetry; consider
   one when the per-CID retrievability checker lands.

2. genesisKind docstring says "'deal' wins on a pathological deal+offer
   collision", but deriveDealCidSnapshot's live-row pinning assigns
   `genesisKind[e.genesis] = e.category` unconditionally, so for a genesis
   with BOTH a live 'deal' and a live 'offer' row the last-processed row
   wins ('offer', since offers iterate after deals in the view). Impact is
   nil in practice (genesis is a deal by construction; the collision is
   treated as pathological everywhere) and emitIncrementalEntries' revoked
   path bypasses genesisKind for such genese anyway (revokedSeen), but the
   comment overstates the guarantee. Cosmetic.

3. Commit-message wording for snapshotToEntries ("deeper-revoked offer
   genesis no longer falls through to 'deal-version'") is imprecise: the
   old code already emitted 'offer-version' for anything not in prev.deals,
   so offers were never wrong. The real behavior change is the deep-revoked
   DEAL case (was 'offer-version', now 'deal-version'). Behavior is correct;
   comment wording only.

4. Pre-existing, not introduced by this fix: coldComplete validates only the
   deal layer vs incremental complete folding in configOk/treeOk/archiveOk
   (doc'd, Finding 3) and the re-walk double root read (doc'd, Finding 4).
