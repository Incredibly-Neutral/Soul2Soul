{ok:false, root:''}; empty -> {ok:true, root:''}; malformed contenthash ->

thrown -> {ok:false, cid:''}; success -> {ok:true, cid} (cid may be ''). The ok flag

Q3 — DOUBLE getConfig (config.ts:61-72): REAL but negligible divergence.
readConfigRoot makes call #1 (config.ts:47), then collectConfigCids re-reads getConfig
for the body (config.ts:70); if call #1 succeeds and call #2 throws, the new code returns
[config entry] (config.ts:72) where the original returned []. Severity: essentially
unreachable in production — the adapter maps getConfig to deps.readConfig() (adapter.ts:39),
a single eth_call; two back-to-back calls both succeed or both throw. It is also
fail-open (emits the entry it successfully read, never throws, never loses data). It is
NOT avoidable without changing the helper contract WHILE routing the collector through
the helper (readConfigRoot exposes only {ok,cid}). Clean fixes: (a) have readConfigRoot
return the config body as an additive field (superset of {ok,cid}, backward-compatible for
the coordinator) and drop call #2; or (b) keep the collector on its own single inline
getConfig and leave the helper for the coordinator alone. Option (a) is cheapest now since
the coordinator branch is not merged. Non-blocking.
