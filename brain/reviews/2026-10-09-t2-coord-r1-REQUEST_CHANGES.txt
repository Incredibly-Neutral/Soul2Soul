1. [BLOCKING] Revoked-genesis version history is retained for exactly ONE
   incremental refresh, then silently vanishes — with meta.complete:true the
   whole time. The restore trace (Q1) does NOT hold for the revoked case, and
   the steady state is non-deterministic (Q5).

   Where: coordinator.ts:237-239 (`prevSnapshot = deriveDealCidSnapshot(prev)`
   then `collectDealCidsIncremental(ctx, prevSnapshot)`), interacting with
   deals.ts:198-224 (`deriveDealCidSnapshot` reconstructs `deals`/`offers` only
   from the prev VIEW's 'deal'/'offer' entries) and deals.ts:283-291
   (`emitIncrementalEntries`'s revoked-retention branch fires only for genese
   present in `prev.deals`/`prev.offers`).

   Repro (empirically confirmed with a scratch fixture; G1 live at cold then
   revoked):
   - cold   : [deal:G1, deal-version:DV, ...]           complete:true
   - inc #1 : [deal-version:DV, deal-version:G1-cur, ...] complete:true  (revoked
             history retained — T1's intended behavior)
   - inc #2 : [ ... no G1 entries at all ... ]          complete:true  ← history
             silently dropped, nothing re-fetches it, no cold fallback
   Reason: after inc #1 the view has no 'deal' row for the revoked genesis, so
   `deriveDealCidSnapshot` can no longer put it in `snapshot.deals`; on inc #2
   the revoked branch of `emitIncrementalEntries` never sees it, and the
   fast-path fingerprint (deals=[] == deals=[]) is equal so it is never diffed.
   Consequence: two consecutive refreshes with identical inputs produce
   different views (inc #1 ≠ inc #2) both marked complete:true — a determinism
   violation (Q5) and a silent data loss the `complete` flag exists to prevent.
   The T1 comment at deals.ts ("Revoked genesis ... history retained") documents
   retention as intended, so the drop contradicts the design.
   Fix direction (for implementer to confirm): carry revoked-genesis knowledge
   across hops (e.g. persist a known-genesis set / retained history in meta or
   derive the snapshot from a state that still lists the revoked genesis), or
   emit revoked history unconditionally in the fast path rather than keying off
   `prev.deals`.

2. [BLOCKING / assess] The documented "accepted known-corner" (asset shadowed
   by a deal entry, then the deal moves without the root changing) is real, but
   my trace shows it is NOT self-correcting, and — worse than the notes claim —
   a layer ROOT CHANGE does not fix it either; it only resolves on a full cold
   rebuild.

   Where: coordinator.ts:284 (archive reuse via `prev.entries.filter(e =>
   e.source === 'archive')` — the pre-folded layer), and coordinator.ts:289-291
   + mergeGroups (deals.ts/coordinator.ts:67-81) for the re-walk case.

   Precise trigger: a deal row cid X shadows an ARCHIVE-ITEM X (identical dedupe
   key `X\u0000G1\u0000''` — deals merge before archive), then the deal is
   revoked. Repro (confirmed):
   - cold (deal live) : deal:X, config, archive:ACID          (archive-item X folded)
   - inc #1 (revoked) : deal-version:X, config, archive:ACID  complete:true
   - inc #2 (steady)  : config, archive:ACID                   complete:true
   - cold rebuild     : config, archive:ACID, archive-item:X   ← ground truth: X IS in the archive
   Even a re-walk (archiveRoot changed to ACID2) does NOT reveal archive-item X:
   the incremental path re-emits the revoked genesis's deal-version X (source
   deals, first in merge order), which re-folds the freshly-collected
   archive-item X. So the corner is persistent (complete:true) and only clears
   on an independent cold rebuild. This is bounded (one item's role hidden, and
   the CID is still listed as a deal-version until inc #2), so it is arguably
   acceptable — but the task's framing "assess whether it is truly
   self-correcting" should be answered NO. At minimum the implementer should
   confirm this matches the accepted trade-off and document that it is not
   self-correcting (otherwise the future per-CID retrievability checker that
   consumes this delta will silently skip the item).

3. [OBSERVATION, not blocking] Complete asymmetry causes a cold-rebuild
   oscillation under a persistently-failing root read (getConfig / ENS
   contenthash). coldComplete (coordinator.ts:136-153) validates ONLY the deal
   layer, so a cold build with getConfig throwing yields config=[] and
   complete:true; the incremental path includes configOk/treeOk/archiveOk in
   `complete` (coordinator.ts:306), so the same throw yields complete:false →
   next refresh cold-rebuilds (complete:true) → next incremental (complete:false)
   → oscillation with a full cold rebuild every other refresh. Confirmed
   empirically (cold:true → inc:false → cold:true → inc:false). The view is
   never WRONG (it matches cold's fail-open output) and this is strictly no
   worse than pre-T2 (which was all-cold), so it is a perf note only. If the
   team wants the incremental benefit to survive transient root failures, make
   cold `complete` reflect config/tree/archive root reads (or vice versa) so the
   two paths agree.

4. [OBSERVATION, minor] On the re-walk branch the root is read twice: e.g. a
   config root change calls `getConfig` in readConfigRoot (coordinator.ts:155)
   and again inside collectConfigCids (config.ts) — confirmed cfgCalls=2 on a
   root change (1 when unchanged). Same for tree/archive getEnsText
   (readEnsRoot + collector). Extra RPCs only on the changed-root path; not a
   correctness issue. Also a degenerate-adapter edge: cold emits a 'config'
   entry even when getConfig returns cid='' (config.ts), while the incremental
   treats cid==='' as absent and drops it — only reachable with an adapter
   returning an empty cid, not worth handling.
